The Phase 2 report states:

`POST …/store-credit-email`

still sends email AND marks sales/items as `STORE_CREDIT`.

This violates the payout invariant established in Phase 2:

**Communication must not itself be the authoritative financial event.**

Audit this route completely.

Determine:

* exactly what financial rows it changes
* whether it credits `consignors.store_credit`
* whether it changes `sales.payout_status`
* whether it changes item status
* whether it writes to `store_credit_usage` or another ledger
* which admin UI calls it

Then separate the behaviours with the smallest safe change.

Required final behaviour:

### Store-credit communication

Email/notification only.

Must not:

* mark sales STORE_CREDIT
* credit a balance
* mark items Paid
* change payout financial state

### Explicit store-credit confirmation

Financial action only.

Must:

* operate on an exact payout run / exact payout-run items
* be transactional
* be idempotent
* update the correct store-credit financial fields exactly once

If the existing run-scoped:

`markRunConsignorStoreCredit`

already provides the correct financial action, use it rather than inventing a second implementation.

Add regression coverage proving email alone is non-financial.

# Concern 2 — Confirm Paid must NOT assemble a payout at confirmation time

The Phase 2 report says:

`confirmConsignorPayoutPaid` ensures eligible sales are inserted into `payout_run_items` before calling the transactional confirmation path.

Audit this carefully.

We do NOT want:

`Confirm Paid`
→ discover all currently eligible pending sales
→ construct payout contents
→ mark them paid

That makes confirmation itself determine the financial scope.

Required invariant:

**The exact payout contents must be fixed BEFORE payment confirmation.**

Preferred flow:

PENDING sales
→ Prepare payout
→ payout run + exact `payout_run_items` created
→ staff reviews exact payout
→ payment performed
→ Confirm Paid using existing run ID
→ only those fixed run items transition

Therefore:

* `confirm-payout-paid` must require an existing payout run ID, directly or through an already-established exact run relationship.
* It must NOT add newly eligible pending sales to the run while confirming.
* It must NOT automatically create a broad payout run during confirmation.
* It must NOT infer payout scope from all current PENDING sales.

If the current admin UI does not prepare a run before calling Confirm Paid, report that workflow and make the minimum safe adjustment required to use the existing payout-run preparation path.

Do not redesign the screen.

# Concern 3 — Invalid run contents must fail atomically, not be skipped

The report states:

"Invalid/missing/wrong-consignor sales are skipped or flagged."

That is not sufficient for a financial confirmation.

For confirmation of a payout run:

If any payout-run item expected to be confirmed is inconsistent, including:

* missing sale
* sale belongs to another consignor
* item mismatch
* unexpected payout status
* amount/snapshot integrity problem where applicable

the operation must:

1. fail
2. roll back the transaction
3. mark none of the payout-run items newly paid

Do NOT silently skip invalid rows and continue paying the rest.

Idempotency is different:

A run already fully confirmed may safely return an already-processed/no-op result.

But a partially inconsistent unprocessed run must fail.

Add a behavioural test demonstrating full rollback.
